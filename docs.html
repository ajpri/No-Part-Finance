No Part Finance Integration API

These public instructions contain fictional examples only. OpenAPI contract. Financial reads and submissions require a configured Owner and an active integration secret.

Setup and permissions

Configure the Owner using startWindows.bat manage-users or ./startLinux.sh manage-users. Sign in as Owner, open Settings → System → Integration Secrets, and create a labeled secret. The Owner can use Edit Label to rename it later, including after revocation; existing proposals display the current label, while credentials and retry identity remain unchanged. Send it only in Authorization: Bearer <secret>. Remote integrations require HTTPS provided by your deployment boundary. Never put credentials in a URL or log.

A secret permits the reads listed below, one ordinary transaction or transfer/payment proposal per submission, reading and updating all current Pending items, and status checks for that secret's own submissions. It grants no browser login, direct ledger creation or editing, approval/rejection, deletes, bulk submissions, reimbursement shortcuts, or configuration, Budget, or Simulator writes. Only the Owner may decide proposals.

Respect signs and units

Read the Category's reportingRole, never its name. Submit amount as a USD string in the entered-amount convention. Do not submit signed ledger cents as entered dollars. Python performs the conversion for both Cash and Credit Accounts:

income: ledger = entered; expense: ledger = -entered. Refunds reduce Expenses; Income reversals reduce Income. Negative does not automatically mean Expense. Ledger amounts, current internal balances, friendly Credit debt display, and projections have different meanings. An internal negative Credit balance is an amount owed; a positive Credit balance is an overpayment credit. Never invert signs based on Account class.

Computed response money uses integer cents; editable Pending amount fields retain entered USD strings. Ordinary history includes amountCents (ledger), enteredAmountCents and displayAmountCents (Category interpretation). Combined valid transfers use an unsigned event amount, represent two ledger rows, and are excluded from Income/Expenses. Invalid linked rows and uncategorized historical activity retain ledger signs. External appears as a System transfer boundary without a financial balance. Current balance includes the Account offset plus all ledger amounts. Simulator results are projections, never current balances.

Amount strings accept strict USD syntax with at most two decimal places, correctly grouped commas, optional dollar prefix, and bounded addition/subtraction expressions. For example "1,000.50", "-$17.27", or "532+110". Letters, malformed grouping, scientific notation, repeated signs, and extra decimal places are rejected, never silently blanked or converted. Zero follows the existing ordinary-transaction rule and is accepted. Date is an explicit ISO calendar date YYYY-MM-DD; future dates and valid leap days are accepted, and there is no inferred agent-local today.

Catalogues and planning/reporting snapshots are complete, unpaginated responses for this small installation; they do not silently truncate totals. Unknown filters are rejected. Boolean configuration flags may be returned as 0/1. IDs are stable database integers.

A positive ID with no matching history returns HTTP 200 with an empty transactions array, total 0, nextOffset null and zero summary values when requested. Account filters match either side of a valid combined transfer; Category filters exclude transfers.

Submit, retry, and check status

POST /api/integration/submissions with exactly these fields; use real eligible IDs from the catalogue rather than assuming the fictional IDs below exist:

{"submissionId":"example-expense-001","date":"2026-10-01","accountId":1,"description":"Example groceries","categoryId":2,"amount":"50.00"}

A transfer contains exactly the following seven fields, including type: "transfer". Do not include Account/Category fields from an ordinary request or a Pin setting. Use distinct positive-integer eligible active From and To Accounts. External may be either side. Amount must be a strictly positive USD string; zero, negative, missing, mixed and malformed fields fail without partial writes. Do not infer transfer type, date or signs from descriptions, names, Account class or balances. No insufficient-funds restriction or payoff default is added.

{"submissionId":"example-transfer-001","type":"transfer","date":"2026-10-02","fromAccountId":1,"toAccountId":3,"description":"Example Cash transfer","amount":"25.00"}

A payment to Credit Card or Personal Loan is the same transfer operation:

{"submissionId":"example-payment-001","type":"transfer","date":"2026-10-02","fromAccountId":1,"toAccountId":4,"description":"Example Card Payment","amount":"50.00"}

Positive "50.00" records From -5000 and To +5000 only after Owner approval. Both ledger rows share Date, Description and transferId, have null Categories and sum to zero. Payments and External transfers affect neither Income nor Expenses.

A successful first submission returns 201 and an object containing id, submissionId, status (Pending), kind (transaction or transfer), transactionId (null), transferId (null), and reviewVersion (initially 0). An identical retry returns 200 with the same identity and current status. Reuse of the same submissionId with different submitted content returns 409. Identity is scoped to one integration secret and survives restart, rejection, approval, and Owner or API correction. Original type is part of identity: reusing an ordinary ID for a transfer conflicts. Keep exactly the same submitted content when retrying after a lost response. Never retry a rejected proposal under a fresh ID to evade the decision.

GET /api/integration/submissions lists only your submissions, using the same pagination envelope with submissions in place of transactions. Optional submissionId matches one exact caller ID and status accepts Pending/Approved/Rejected. Approved entries include the created transactionId; it can become null if the ledger event is subsequently deleted. Approved transfers return transferId and null transactionId. Pending/Rejected transfers have both ledger identifiers null. The approved transferId remains after later deletion, although its ledger lookup may find no rows. Status remains Approved and a retry does not recreate an ordinary event or transfer.

Read and update any Pending item

GET /api/integration/pending returns all current Pending transactions and transfers: any integration’s proposals, Manual Save as Pending entries, events moved from the ledger, and items already edited by the Owner. It returns count, transactionCount, transferCount, and rows containing current fields, stable id, kind, source/label, pin state, reviewVersion, and Reporting Role/validation metadata. An empty queue returns zero counts and rows: []. No query parameters or pagination. This read exposes no terminal history, secrets, credentials, original payloads, or private move snapshots.

PUT /api/integration/submissions/{proposalId} updates one of those items using its id in the path. Send every editable field plus the current reviewVersion. For ordinary items, send reviewedRole from the selected Category’s current reportingRole; do not infer it from names or signs. For transfers, omit reviewedRole and keep a positive Amount. The following examples use fictional IDs and versions; obtain current values from the Pending read and catalogues:

{"date":"2026-10-01","accountId":1,"description":"Corrected example groceries","categoryId":2,"amount":"45.00","reviewedRole":"expense","reviewVersion":0}
{"date":"2026-10-02","fromAccountId":1,"toAccountId":3,"description":"Corrected example transfer","amount":"30.00","reviewVersion":0}

Do not send submissionId, id, kind, type, Pin, source, status, or attribution fields in the update body. No partial/bulk updates or query parameters. Python uses the same financial validation and atomic save as Owner review. Success returns 200 with {"reviewVersion":1} (the newly advanced version), and the item stays Pending. Every successful save advances the version, including an unchanged save. Your update invalidates an older Owner review; Owner saves likewise invalidate an older API update. A stale request or lost-response retry returns 409. Re-read Pending and reconcile; never automatically substitute a newer version to force an overwrite. Owner-edited items remain API-editable.

Updates preserve the original submitted/move identity, source attribution, Pin and private snapshots and affect no ledger, balance, report, Budget or Simulator state. They never generate a new description or reverse signs automatically. Approval/rejection stays Owner-only; terminal items cannot be updated. Moved events still receive new ledger IDs only on Owner approval and never automatically regain old Simulator links. Existing changed-Reporting-Role warnings remain for explicit Owner sign review. Existing GET /api/integration/submissions remains limited to your own submission statuses, now including reviewVersion; original POST retries keep their existing identity and behavior.

Human review remains authoritative

Pending or rejected proposals affect no balance, report, Budget or Simulator total. One Owner-only Pending page has Transactions (count) and Transfers (count) sections with shared selection and decisions. Ordinary rows retain Date, Account, Description, Category and entered Amount. Transfer rows show Date, From Account, To Account, Description and positive Amount. A proposal’s kind is fixed; corrections cannot convert it. In Pending transfer review, explicitly changing To Account updates the editable Description using the normal transfer/payment destination wording. Changing From Account or merely loading review preserves it. Each transfer row has Use default description to regenerate just that row’s editable Description from its current destination. This changes only the review draft; it does not save, approve, alter other fields or rows, or offer a reset-all action. Cancel Changes restores saved values; this never changes the integration’s original retry content. Validation errors and changed-Reporting-Role warnings appear inline only when needed, without a separate ledger-preview column. Valid submitted values are retained. The Owner can save corrected rows while leaving them Pending, or cancel unsaved changes back to the last saved values. Saved corrections survive restart and do not replace original retry content or create ledger activity. Stale saves and decisions conflict if another view has saved newer corrections. Unavailable configuration is flagged for correction. A Category Reporting Role change is clearly flagged, with its original and current role; the Owner checks the current sign and explicitly approves that reviewed role. Malformed corrections are flagged and cannot be approved. If a Category changes again during review, approval fails until refreshed review. No silent reinterpretation or implicit approval occurs.

Approve All Pending requires all rows to be saved and valid, then asks the Owner to confirm the combined total and transaction/transfer breakdown. Each transfer counts once despite its two ledger rows. Dashboard shows Pending review and Transactions retains Review Pending (total), including zero. No combined financial dollar total is added. Cancel writes nothing. A changed queue or stale saved row prevents the entire approval. Approval revalidates current eligibility, saved fields, revisions and financial meaning and inserts ordinary rows and both sides of each transfer, with proposal decisions, in one SQLite transaction. Selected batches may mix kinds and sources. A failed item rolls back the entire selected set. Concurrent or repeated approval cannot duplicate ledger rows. Reject writes no ledger activity.

Manual Pending entries and moved events

The signed-in Owner may use Save as Pending in the existing new ordinary/transfer forms instead of direct ledger Save. Date defaults to browser-local today, remains editable (including future dates), and is preserved on approval. Templates remain editable presets and ordinary Pin is retained. These durable items have the fixed source Manual, per-entry retry identity, saved review corrections and the same review/counts/atomic decisions. They never execute automatically. Paired Also log reimbursement must be unchecked to save one Pending item; it is never silently omitted.

Move to Pending applies to persisted categorized ordinary events and valid transfers/payments, after saving or cancelling editor changes and explicit confirmation. It captures the original Date, fields, entered signs and ordinary Pin, removes the ledger event immediately from balances/reports and resets every linked Simulator row to Planned with cleared links and unchanged saved planner values, atomically. Offsets and uncategorized legacy balance history stay unchanged. Simulator rows contribute to projections again; approval creates new ledger IDs and never automatically relinks them. Rejection leaves the event removed. Archived references remain visible for explicit correction. Original integration proposals stay Approved, with the deleted-ledger identifier rules above; a new independent Manual proposal is reviewed. Stale source snapshots fail, and per-move identity prevents duplicate moves or removal of a reused ledger ID.

Auditors cannot review or decide proposals. Bearer integrations cannot create Manual entries, move ledger events, or decide proposals; they can read and update every current Pending item, including Manual items. Public OpenAPI includes only supported Bearer operations, not Owner browser endpoints. Agents cannot claim Manual attribution.

Errors and credential backups

Errors use {"error":"concise explanation"}: 400 malformed fields/filters or current validation failure; 401 missing, invalid or revoked Bearer secret; 403 prohibited operation; 404 unknown integration read resource or missing Pending proposal ID; 409 conflicting retry, stale/invalid reviewVersion, terminal update target, or changed reviewed Reporting Role; 413 oversized request; 503 no configured Owner; 500 unexpected failure without private details.

Submission and Pending-update bodies are limited to 1 MiB (1,048,576 bytes). An authenticated request above that limit returns HTTP 413 with application/json and {"error":"Request exceeds the 1 MiB limit"}, creating or changing no proposal or ledger records. A body exactly at the limit still undergoes normal parsing and validation. Authentication and Owner-configuration failures retain their existing precedence.

Secrets are stored recoverably in SQLite without a separate encryption key. Treat finance.db, migration backups, downloaded database backups and packages containing the database as credentials as well as financial data. They include password hashes, recoverable integration secrets, their active/revoked state, proposals and retry identities. Application-only packages include none of that runtime state. Restore a backup to the exact configured database path while the application is stopped, preserving the old database and any associated SQLite sidecars first. See README.md, Backup and restore, for the full procedure and known upgrade-failure limitation. Restoring an older backup restores its credential state and may reactivate a secret revoked after the backup. Revoke it again after restore. Browser sessions do not survive restart. Revocation immediately blocks subsequent API requests but retains prior proposals and labels for Owner review.
